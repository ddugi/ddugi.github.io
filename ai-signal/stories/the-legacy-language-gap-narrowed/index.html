Models / Coding models for low-resource and legacy programming languagesImportantReported signal

The legacy-language gap narrowed.

OpenAI reports large gains on two new coding evaluations covering 20 programming languages and behavior-preserving COBOL migration. The strongest result is not that a model can translate old syntax. It is that models are being tested against observable behavior in languages that run essential systems—while production correctness, independent replication, and benchmark breadth remain open.

01 / Evidence boundary

Verified facts

  • OpenAI published its low-resource programming-language results on 19 October 2026 and described two evaluations: MultiLangBench for building SQLite-compatible engines across 20 languages, and a COBOL migration evaluation for behavior-preserving translation. [openai-low-resource-languages] [openai-multilangbench]
  • OpenAI reports that GPT-6 Astra at maximum reasoning effort averaged an 87.4% test pass rate across 20 MultiLangBench languages, compared with 26.8% for GPT-5.6 Sol, with improvements in every tested language. [openai-low-resource-languages]
  • The reported MultiLangBench gains include COBOL from 10.9% to 72.1%, OCaml from 25.6% to 85.8%, Fortran from 21.4% to 83.5%, and Visual Basic from 27.5% to 89.4% when comparing GPT-5.6 Sol with GPT-6 Astra. [openai-low-resource-languages]
  • OpenAI reports that GPT-6 Luna averaged 40.3% on MultiLangBench at maximum reasoning effort and an estimated $0.77 API cost per sample, compared with $3.48 for GPT-5.6 Sol—approximately 78% lower. [openai-low-resource-languages]
  • On OpenAI's COBOL migration evaluation, GPT-6.1 Sol reportedly reached 86.6% accuracy at low reasoning effort versus 5.4% for GPT-5.6 Sol at the same setting, at 61% of the estimated API cost; higher reasoning effort reached 97.9%. [openai-low-resource-languages]
  • The migration evaluation uses hidden tests and requires byte-for-byte parity on observable outputs; a migration counts as successful only when every test passes. [openai-low-resource-languages]
  • The public MultiLangBench repository says its tests derive from SQLite 3.40.1's TCL suite, that 24,000 tests were converted, and that normal evaluation should use the 272 tests whose identifiers begin with 00, 01, or 02 unless a larger run is explicitly reported. [openai-multilangbench]
  • The public evaluation setup gives the model SQLite documentation, removes SQLite implementations from the environment, prohibits internet access, and grades candidate database files against the reference SQLite binary. [openai-multilangbench]
Reporting context

OpenAI introduced MultiLangBench and a COBOL migration evaluation to test whether current models can build working software and preserve legacy behavior across languages with less training data and tooling support.

02 / Observed change

What actually changed

Evaluation moved beyond popular-language issue fixing into two harder enterprise-shaped questions: can a model build substantial behavior across languages with sparse training material, and can it migrate legacy programs without silently changing their outputs? OpenAI also released the MultiLangBench harness, making part of the claim inspectable instead of publishing only a scoreboard.

03 / Interpretation

Why it matters

Legacy modernization fails when a rewrite compiles but changes a rounding rule, missing-record path, or decades-old business invariant. Testing exact observable behavior is closer to the real risk than measuring syntactic translation. If the reported gains transfer beyond the benchmark, engineering teams could use models to investigate and migrate systems that have limited documentation and shrinking expert capacity—but only with the old system serving as an executable specification.

04 / Engineering analysis

Technical implications

Use coding models as migration workers inside a verification harness, not as authorities on legacy behavior. Capture characterization tests before rewriting, compare outputs at byte and business-rule level, preserve build and runtime constraints, and require domain experts to review mismatches. Re-run the public benchmark in the target environment and build repository-specific evaluations; a SQLite-compatible engine and small COBOL programs do not establish correctness on a production estate.

05 / Potential beneficiaries & pressure

Business implications

Better support for COBOL, Fortran, Visual Basic, and other underrepresented languages could expand where AI-assisted maintenance and modernization are economically plausible. The value depends on verification cost, unavailable specifications, integration complexity, and expert review. A cheaper generated rewrite that creates reconciliation errors or operational risk is not a modernization saving.

06 / Possibility, not certainty

Where this could be going

Conditional outlook · Not a fact

Conditional outlook: if independent teams reproduce these results and enterprise pilots show lower migration effort without increasing escaped defects, low-resource-language capability could become a practical modernization tool. If performance depends on narrow benchmark structures, familiar SQLite behavior, or small isolated programs, the gains may improve demonstrations long before they reduce the risk of replacing critical systems.

07 / What could change the picture

Risks & uncertainties

  • The headline results were produced and published by the model provider; no independent replication is linked.
  • MultiLangBench measures construction of one SQLite-compatible system, which may not represent maintenance, debugging, dependency integration, or business-rule recovery in real repositories.
  • The repository documents a 272-test standard subset from 24,000 converted tests; the publication does not make run variance or sensitivity to test selection visible.
  • SQLite behavior and documentation are widely available, so removing runtime implementations and internet access does not eliminate training-data familiarity or benchmark-specific learning.
  • The publication releases MultiLangBench but does not link a public COBOL migration dataset and harness, limiting reproduction of the strongest migration result.
  • A 97.9% score near evaluation saturation can indicate strong capability, a narrow benchmark, or both; it does not quantify the severity of the remaining failures.
  • Byte-for-byte output parity covers tested observable behavior, not undocumented operational dependencies, performance, security, batch scheduling, data quality, or downstream contracts.
  • The cost comparisons are estimated API costs for benchmark samples and do not include test creation, expert review, failed migrations, integration, or production assurance.
08 / Editorial analysis

The AI Signal take

The useful idea is not 'AI understands COBOL now.' It is that legacy code should be judged by what it does, not whether a generated rewrite looks modern. OpenAI's numbers suggest the model gap is narrowing. The evaluation boundary says what still matters: executable tests, exact outputs, and experts who know which hidden behavior cannot be lost.
