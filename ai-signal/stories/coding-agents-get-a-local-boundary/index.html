The agent boundary now reaches the desktop.

GitHub added computer use to Copilot after introducing local sandboxing and enterprise rollout policy. The control plane now has to govern screen context and actions inside desktop applications.

01 / Evidence boundary

Verified facts

  • GitHub announced local sandboxing in the GitHub Copilot app on 23 September 2026. [github-local-sandbox]
  • Project settings can restrict additional filesystem paths, outbound and local-network access, and availability of Git and GitHub CLI credentials. [github-local-sandbox]
  • GitHub says enterprise-managed settings can make the effective policy more restrictive than the project requests. [github-local-sandbox]
  • GitHub says the sandboxed shell fails instead of running without a sandbox when the operating system cannot enforce the requested policy. [github-local-sandbox]
  • Local sandboxing is off by default, applies to new or restarted local sessions, does not cover cloud or remote-host sessions, and remains in public preview. [github-local-sandbox]
  • GitHub announced a global default policy for eligible generally available Copilot features on 24 September 2026. [github-copilot-default-policy]
  • Enterprises can set eligible current and future features to enabled, disabled, or delegated to organization administrators; the policy is scheduled to take effect on 22 October 2026. [github-copilot-default-policy]
  • GitHub says explicit feature decisions and preview opt-ins are preserved, and that the default covers eligible feature controls, Copilot code review, and MCP-server policy. [github-copilot-default-policy]
  • GitHub announced computer use on 1 October 2026 in public preview for Copilot CLI and the Copilot app on macOS and Windows. [github-computer-use-release]
  • GitHub says computer use can read accessible content and visual context, then click, type, scroll, drag, and navigate across desktop applications. [github-computer-use-release] [github-computer-use-docs]
  • Computer use is disabled by default and follows Copilot Tool Permissions, with approval available for one session or as a saved always-allow decision. [github-computer-use-docs]
  • GitHub documents that saved approvals apply to Copilot CLI and the Copilot app on the same machine, and that removing a saved approval does not revoke access in a session already running. [github-computer-use-docs]
  • GitHub documents an enterprise-managed computer-use setting that can prevent users from enabling the feature locally. [github-computer-use-enterprise-settings]
  • GitHub warns that changing interfaces, timing, and window state can produce wrong or repeated actions, and that visible sensitive information may be provided as model context. [github-computer-use-concepts]
Reporting context

GitHub released computer use in public preview for Copilot CLI and the Copilot app on macOS and Windows, allowing an approved agent to interact with desktop applications through their visual interface.

02 / Observed change

What actually changed

An agent can now read accessible content and visual context, then click, type, scroll, drag, and navigate across desktop applications. The operating boundary expands from files, networks, credentials, and tools to screen contents, application controls, OS permissions, and active-session revocation.

03 / Interpretation

Why it matters

Visual control can reach legacy and GUI-only systems without waiting for an API or integration project. It also gives an uncertain model the same interface used for email, finance, administration, and internal data. A wrong click can become a real business action.

04 / Engineering analysis

Technical implications

Approve applications individually, avoid persistent approval for sensitive software, and use enterprise policy to disable computer use where the risk is unacceptable. Prefer APIs, MCP, terminals, and filesystem tools when they offer a structured path. Test stop behavior, record effective permissions, and remember that removing a saved approval does not revoke a running session.

05 / Potential beneficiaries & pressure

Business implications

Teams may automate work in software that was previously too old, closed, or expensive to integrate. The trade-off is a wider operational blast radius: actions execute with the user’s access and can expose visible company or third-party data to the model.

06 / Possibility, not certainty

Where this could be going

Conditional outlook · Not a fact

Conditional outlook: if desktop agents gain reliable action confirmation, centralized approval inventory, narrow screen-context controls, and auditable session revocation, they could become a practical bridge to legacy systems. If interface changes and broad saved approvals remain hard to govern, structured integrations will stay safer for important workflows.

07 / What could change the picture

Risks & uncertainties

  • Local sandboxing remains a public preview, is off by default, and provides no independent escape-testing results in the cited release note.
  • The global rollout policy does not take effect until 22 October 2026, so this draft cannot verify its behavior across a real enterprise estate.
  • Eligibility rules and exceptions can change which controls inherit the default; administrators still need an effective-policy inventory.
  • Local, cloud, remote-host, app, and CLI sessions have different control paths, which can produce inconsistent protection.
  • A permissive global default or broadly available Git credentials can turn centralized convenience into a larger blast radius.
  • Computer use is in public preview and the cited material contains no independent reliability or security evaluation.
  • Changing layouts, timing, focus, and window state can lead to a wrong control, wrong text location, or repeated action.
  • Screen and accessibility context can include sensitive company or third-party information unrelated to the intended task.
  • A saved approval broadens future access on the same machine, while removing it does not stop access inside an already-running session.
  • Application approval and enterprise policy do not by themselves guarantee least privilege or a fresh confirmation before a high-impact transaction.
08 / Editorial analysis

The AI Signal take

The breakthrough is reach, not precision. A visual agent can use almost any software a person can see, but that flexibility removes the guardrails supplied by a typed API. Desktop access should be treated as a privileged capability, not a convenient fallback.
