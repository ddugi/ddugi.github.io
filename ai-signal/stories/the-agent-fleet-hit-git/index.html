Infrastructure / Source-control infrastructure for thousands of concurrent coding agentsStructural ShiftReported signal

The agent fleet hit Git.

OpenAI rebuilt its source-control backend after concurrent Codex work overwhelmed its monorepo service. GitHub has now published the storage architecture behind the same bet: disposable compute, object storage, per-reference consensus, and separate maintenance workers. The signal is no longer just traffic growth; source control is becoming distributed systems infrastructure for automated writers.

01 / Evidence boundary

Verified facts

  • OpenAI published Pando on 2 November 2026 as a Git-compatible repository backend that now serves all development in its monorepo. [openai-pando]
  • OpenAI says increased parallel work from Codex produced more branches, pushes, merges, fetches, clones, and CI fan-out, while its previous source-control system at times fell below 90% reliability. [openai-pando]
  • Pando stores incoming packfiles as immutable blobs, records versioned reference metadata, serializes updates to each reference, and relaxes repository-wide point-in-time consistency so unrelated branches can move independently. [openai-pando]
  • OpenAI reports that moving to Pando reduced median push latency by nearly 80%, improved merge reliability, and enabled delivery of about one petabyte of Git data per day; these are first-party production measurements, not independent benchmarks. [openai-pando]
  • OpenAI says Pando began serving production traffic in April 2026, was built in ten weeks, retains the Git protocol and client workflow, and has contributed several client improvements upstream or through a public Git patch tracker. [openai-pando]
  • GitHub separately said on 6 October 2026 that agentic development was driving a Git architecture redesign focused on concurrent writes, CI read fan-out, storage and compute separation, background maintenance, and preserving branch protection and audit controls. [github-agent-scale-git]
  • GitHub reported that pushes grew from 0.69 billion to 3.35 billion per month between September 2025 and August 2026 and that developers and agents made 7.38 billion commits in September 2026; GitHub did not separate the human and agent shares of those totals. [github-agent-scale-git]
  • GitHub published the end-state design of its new Git storage architecture on 5 November 2026 and says it is available in limited private preview, with broader rollout planned for early 2027. [github-rubicon-git-storage]
  • In internal testing, GitHub says the system supported 5,000 concurrent agents on one repository and 7,200 pushes per second while maintaining consistently low read latency; these are vendor-run load tests, not public production measurements. [github-rubicon-git-storage]
  • GitHub's architecture stores pack data in Azure Blob Storage, keeps authoritative reference and pack-manifest state in a replicated compare-and-swap log called Ref-CAS, and serves requests through disposable virtual replicas whose local disks are rebuildable caches. [github-rubicon-git-storage]
  • Ref-CAS orders updates per reference instead of serializing the whole repository. GitHub says reference-state transactions can run in the tens of thousands per second because agents usually push to separate branches and therefore do not contend. [github-rubicon-git-storage]
  • Dedicated compaction and garbage-collection workers operate directly against durable storage rather than consuming the compute that serves reads and writes, allowing maintenance throughput to scale separately. [github-rubicon-git-storage]
  • GitHub says requests to one high-traffic repository grew from an average of 44 million per day in March 2026 to 181 million in May, while noting that its busiest repositories still receive at most dozens of writes per second today. [github-rubicon-git-storage]
  • GitHub lists clone-free agent reads, an atomic commit API, event streams, partial replicas, and global replicas as planned follow-on work rather than generally available capabilities. [github-rubicon-git-storage]
Reporting context

One engineer supervises many coding agents. Each agent creates branches, pushes checkpoints, triggers CI, fetches shared history, and competes to merge. A workflow that felt fast for humans becomes an infrastructure bottleneck when the same actions happen continuously and in parallel.

02 / Observed change

What actually changed

OpenAI's production Pando account established that agent concurrency can overwhelm conventional repository assumptions. GitHub has now supplied the hosting-platform architecture and internal load target: thousands of concurrent writers on one repository, independently scalable reads and writes, and background maintenance removed from the request path. The existing signal has moved from design intent to a concrete limited-preview system.

03 / Interpretation

Why it matters

Coding agents multiply branches, checkpoints, pushes, fetches, CI runs, and security scans. GitHub's design shows that the pressure is not solved by a faster disk or a larger server; object storage, reference ordering, caching, compaction, and tenant fairness must scale independently. Most teams will never need this backend, but every platform team will feel some version of its fan-out problem.

04 / Engineering analysis

Technical implications

Measure write concurrency, reference contention, fetch amplification, merge delay, CI fan-out, pack growth, compaction, and cache behavior before changing architecture. At extreme scale, keep immutable objects in durable object storage, order only the reference state that requires consensus, make serving nodes disposable, and move compaction and garbage collection off the request path. Preserve branch protection, audit, and standard Git clients across the change.

05 / Potential beneficiaries & pressure

Business implications

The model bill is only one part of agent-scale development. Source control, CI, review, scanning, storage, and merge coordination become capacity-planned platform services. Hosted providers may absorb the deepest storage redesign; enterprises still need budgets, concurrency limits, repository boundaries, and observability so agent activity does not turn into hidden infrastructure cost or reviewer overload.

06 / Possibility, not certainty

Where this could be going

Conditional outlook · Not a fact

Conditional outlook: if GitHub's limited preview reproduces its internal tests under diverse customer workloads, code hosts will expose more agent-native operations such as atomic multi-file commits, event streams, server-side context access, and lighter clones. If sustained concurrency remains concentrated in a small number of extreme repositories, the architecture will matter mainly inside hosting platforms while ordinary teams gain more from batching and limits.

07 / What could change the picture

Risks & uncertainties

  • Pando's performance and reliability figures are reported by OpenAI and have not been independently reproduced.
  • OpenAI's monorepo and GitHub's highest-volume repositories are extreme workloads; their bottlenecks may not generalize to ordinary engineering teams.
  • Pando is an internal production system, not a generally available product, and OpenAI only says it is exploring ways to share the technology.
  • Pando deliberately gives up a repository-wide point-in-time view of all references during Git operations; other workloads may require stronger consistency.
  • GitHub's redesign corroborates the workload direction but uses a different architecture and was described as work in progress.
  • GitHub's activity totals combine developers and agents, so they do not quantify how much of the growth agents caused.
  • Higher source-control throughput does not solve review quality, unsafe changes, merge correctness, CI cost, secret exposure, or excessive agent work.
  • Software teams can often reduce pressure through batching, concurrency limits, shallow or partial clones, caching, repository design, and CI changes before replacing backend infrastructure.
  • GitHub's 5,000-agent and 7,200-push-per-second figures come from internal testing; the source does not provide a reproducible public benchmark or customer workload distribution.
  • The new architecture is in limited private preview, so broad production reliability, operational cost, and migration behavior remain unproven publicly.
  • The high-traffic repository example shows read growth but does not isolate the share caused by agents, CI, users, or other automation.
  • Clone-free work, atomic commit APIs, event streams, partial replicas, and global replicas are roadmap items and should not be described as shipped features.
08 / Editorial analysis

The AI Signal take

The design principle is wonderfully small: coordinate only what must agree. Git objects are immutable; branch pointers are not. Once GitHub split those responsibilities, storage, request serving, and maintenance could scale on separate tracks. That is the broader agent-infrastructure lesson—automated work turns every unnecessary shared lock into a product limit.

09 / Provenance

Sources & publication record

OpenAI and GitHub provide independent first-party production and architecture accounts of the same workload direction. GitHub adds specific internal load tests and a limited-preview design; OpenAI adds production reliability and latency results. Neither source proves that ordinary repositories need this scale, and both organizations are unusually large agent users with vendor incentives.
