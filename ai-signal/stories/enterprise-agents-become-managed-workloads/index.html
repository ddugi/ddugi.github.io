The agent is becoming a managed program.

Microsoft packaged persistent agents with runtime, identity, inventory, and billing. GitHub now lets teams define repeatable multi-agent work in code with checkpoints and limits. The prompt is becoming an operating process.

01 / Evidence boundary

Verified facts

  • Microsoft announced the new Copilot with Home, Code, and Autopilot on 25 September 2026. [microsoft-new-copilot]
  • Microsoft says Code can build apps, dashboards, automations, and workflows in a sandboxed environment that can be hosted inside a customer tenant. [microsoft-new-copilot]
  • Microsoft introduced Copilot Managed Runtime in public preview as a Microsoft-hosted environment with Entra identity, tenant policies, governed data access, lifecycle management, and centralized inventory. [microsoft-managed-runtime]
  • Microsoft describes Autopilot as a cloud-hosted agent with its own identity, memory, computer, and workspace; it is scheduled to expand to private preview at the end of September. [microsoft-new-copilot]
  • Microsoft says Cowork, Code, Autopilot, and frontier-model use will use usage-based billing, with administrator spending policies, model-family controls, and user-visible credit balances. [microsoft-new-copilot]
  • GitHub announced dynamic workflows on 1 October 2026 for Copilot CLI, the GitHub Copilot app, and the GitHub Copilot SDK. [github-dynamic-workflows-release]
  • GitHub defines a dynamic workflow as code that combines deterministic operations with one or more agents running sequentially, in parallel, or both. [github-dynamic-workflows-release] [github-dynamic-workflows-docs]
  • GitHub documents structured stage results, subagent verification, user input, and pause-and-resume checkpoints as supported workflow behavior. [github-dynamic-workflows-docs]
  • GitHub says workflow subagents inherit the permission grants of the starting CLI session, while an extension can also execute its own code outside agent permission prompts. [github-dynamic-workflows-docs]
  • GitHub documents limits for concurrent and total subagents, active runtime, and approximate AI-credit consumption, and warns that delayed usage reporting can let a run exceed its credit limit. [github-dynamic-workflows-docs]
  • GitHub labels dynamic workflows as a public preview subject to change. [github-dynamic-workflows-release]
Reporting context

GitHub released dynamic workflows for Copilot CLI, the Copilot app, and the Copilot SDK, allowing deterministic code and one or more agents to share a reusable process.

02 / Observed change

What actually changed

Persistent agents now have both an operating envelope and a programmable process. Microsoft supplies tenant runtime, identity, inventory, policy, and billing; GitHub adds code-defined steps, parallel agents, structured handoffs, human checkpoints, resumable runs, and configurable limits.

03 / Interpretation

Why it matters

A prompt can suggest a plan, but it does not make a repeatable operating procedure. Code-defined stages make the control path inspectable: teams can decide where agents reason, where deterministic code validates, where a human approves, and what stops an expensive or risky run.

04 / Engineering analysis

Technical implications

Treat workflow definitions as production code. Pin or record extension, model, tool, and policy versions; test with limited scope; validate structured outputs before downstream use; and log every stage, permission decision, checkpoint, and resume. Review extension code separately because it may run outside agent permission prompts.

05 / Potential beneficiaries & pressure

Business implications

Reusable workflows can turn expert operating procedures into repeatable software and reduce coordination work across reviews, releases, research, and incident response. They also create a new internal software estate that needs ownership, support, change control, budget limits, and retirement rules.

06 / Possibility, not certainty

Where this could be going

Conditional outlook · Not a fact

Conditional outlook: if teams can centrally inventory workflows, reproduce runs, constrain permissions, and measure outcomes, agent orchestration may become a normal automation layer between scripts and full applications. If definitions drift or extension privileges are hard to audit, organizations will inherit another class of fragile shadow automation.

07 / What could change the picture

Risks & uncertainties

  • Code, Autopilot, and Copilot Managed Runtime are in staged rollout or preview, so the announcement does not establish production reliability or broad customer adoption.
  • Microsoft describes inherited governance and tenant boundaries but the cited material does not provide independent isolation tests, incident data, or detailed recovery behavior.
  • A persistent agent can amplify stale instructions, excessive permissions, or incorrect memory over time even when its runtime is centrally managed.
  • Usage-based billing exposes spend controls but can also make the cost of long-running work less predictable than a user subscription.
  • Lowering the barrier to internal application creation can increase the number of unsupported tools, duplicated workflows, and unclear business owners.
  • Dynamic workflows are in public preview, so interfaces, storage, control behavior, and compatibility may change.
  • A reusable definition does not guarantee reproducible results because models, tools, external services, and agent judgments can change between runs.
  • Inherited session permissions and extension code create separate trust paths; a visible agent approval boundary may not cover everything the extension itself can execute.
  • The AI-credit limit is approximate rather than a hard ceiling because usage can be reported after work has already started.
  • The cited sources describe product behavior but do not provide independent reliability, security, or cost measurements from production deployments.
08 / Editorial analysis

The AI Signal take

The important shift is from asking an agent to improvise a process to writing the process down. That gives teams a place to insert checks, limits, and human judgment. It also removes an excuse: once the workflow is code, its permissions and failures belong to an owner.
