OPEN RESEARCH
Protocol before conclusions.
01 / Executive summary

Measure the system around the model.

The proposed study asks what changes operationally when an application moves from a conventional service to an AI-enabled system.

We define an “infrastructure tax” as the incremental operational burden relative to a declared baseline. This is a measurement question, not a claim that AI necessarily increases every cost—or that any added cost is unjustified.

The protocol separates deployment effort, runtime behavior, maintenance work, and application quality. It compares a conventional service, a managed-model integration, and a retrieval-augmented variant under documented workloads.

Incremental burden = AI configuration − declared baseline

Compute differences separately for each metric. Do not combine engineer-hours, latency, and currency into an undefined aggregate score. Value and quality must be evaluated alongside overhead.

02 / Research questions

Three questions to test.

  1. Where does operational work accumulate? Separate one-time setup from recurring deployment, observability, evaluation, and incident tasks.
  2. What changes as architecture grows? Compare a managed-model integration with the same integration plus document ingestion and retrieval.
  3. What does the added complexity buy? Report task quality alongside latency and cost so that overhead is not interpreted without utility.
03 / Methodology

A controlled comparison, with visible assumptions.

Proposed task: answer questions over a fixed, versioned document corpus. The conventional baseline returns search results; AI variants generate answers. These outputs are not functionally identical, so usefulness will be scored separately against a shared task rubric.

Proposed procedure

  1. Freeze the specification. Record the corpus hash, task set, scoring rubric, infrastructure, model identifier, prompts, region, load profile, timeout, and retry policy before data collection.
  2. Run a pilot. Estimate variability and select a repetition count and confidence-interval method before the confirmatory runs. Record changes to this draft in version control.
  3. Compare paired workloads. Use the same questions and concurrency levels; randomize configuration order. Separate warm-up from measurement and identify warm-cache and cold-cache runs.
  4. Measure operations. Log setup and maintenance time with a fixed task checklist. Exercise documented failure scenarios in an isolated test environment.
  5. Analyze transparently. Report failures, retries, sample counts, uncertainty, and raw per-run values. Compare A–B and B–C differences without treating every difference as a causal AI effect.

Latency, errors, traffic, and saturation provide the runtime measurement frame [1]. Proposed instrumentation uses traces, metrics, and logs [2].

06 / Reproducibility

A result should come with a route back to the evidence.

The repository currently contains this publication and an empty measurement template. A reproducible benchmark will require the following artifacts before findings are published:

  • Environment: pinned dependencies, deployment manifests, service versions, and resource sizes.
  • Inputs: corpus provenance and permissions, hashes, task set, prompts, and evaluation rubric.
  • Execution: runner commands, seeds where supported, retries, timeouts, repetitions, and failure scenarios.
  • Evidence: sanitized raw measurements, cost accounting, exclusions, and quality scores.
  • Analysis: scripts that regenerate every table and figure from the released data.

How to use the measurement template

Create one row per measured run. Use configuration IDs A, B, or C. Record UTC timestamps and monetary values in USD, retaining the exchange-rate basis in the run manifest if needed. Keep the manifest and raw evidence in a versioned release. Blank values mean unavailable, never zero.

The file intentionally contains only a header. It is a starting schema, not an executable benchmark or a completed dataset.

07 / Limitations

What this study would—and would not—establish.

A single workload cannot characterize enterprise AI as a whole. Team familiarity, cloud region, service quotas, provider changes, cache state, and model quality can change the observed differences.

The search baseline and generative configurations offer different functionality. Their cost difference is descriptive; it is not automatically a measure of waste. Managed services also shift some work to providers rather than removing it.

Security and governance effort should be documented explicitly. NIST AI RMF 1.0 is background for structuring that discussion [3], not a certification or compliance claim. This protocol does not evaluate organizational or legal compliance.
